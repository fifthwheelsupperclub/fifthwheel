# W07.5 Refund ledger and worker contract

Status: implementation in progress; migration is a draft and is not applied. No Stripe, email, or database calls have been made for this slice.

This contract extends the payment obligations from W07.2 and W07.4. `app_payments` is the verified paid-amount authority; `app_refund_obligations` is the durable amount owed; W07.5 adds durable provider operations and queued work. The migration depends on W07.2’s `app_payments` / `app_refund_obligations` and W07.4’s `source='cancellation'`. Keep migrations unapplied until coordinator review and explicit local authorization.

## Financial invariants

- All amounts are integer USD cents. Payment balance is the verified `app_payments.amount_cents`, never a client value.
- Serialize every obligation/operation mutation by locking its Payment row before obligations and operations. Competing decisions, Table cancellation, refund dispatch, settlement, and correction must use the same Payment-first money lock order after any required Table/Seat locks.
- At all committed states, the sum of non-waived obligations plus other verified refunds cannot exceed the verified paid amount. A refund operation is an allocation against its obligation, not a second obligation. It must fit within that obligation's unpaid remainder and the payment's remaining amount.
- `open`, `pending`, `submitted`, `unknown`, and `failed` obligations remain owed and reserved. Provider-confirmed `succeeded` operations count as refunded; failed-but-still-owed allocations continue to count as reserved. A refund is not shown as complete until provider truth confirms success.
- A Table cancellation adds only the payment's uncovered remainder. It may not duplicate a cancellation or late-payment obligation.
- A definitive provider failure stays reserved. Reusing the same operation retries with the same amount and Stripe idempotency key. An explicit cancel/correct/waive path, if added, must require a bounded reason, actor authorization, operation ID, conflict-safe replay, and audit. W07.5 does not expose an unreasoned balance-release action.

## State and recovery

`RefundOperation.state`: `pending` (durable allocation/work queued) → `submitted` (provider returned an accepted Refund that is not settled) → `succeeded` (provider confirms settlement); `pending|submitted` → `unknown` on timeout/network/5xx uncertainty; `pending|submitted|unknown` → `failed` only on authoritative definitive provider failure. Retry to `pending` is allowed only when the same operation UUID/body can be reused and no provider Refund ID exists. A failed Refund object with an ID is non-retryable and remains owed; admins may reconcile that exact object, while the policy for transferring its reserved allocation to a new operation remains a human decision. No new operation/idempotency key may replace an unknown outcome. A provider-created refund ID is unique within provider mode/account and bound to one operation.

`RefundObligation.state` is a projection of the durable amount due and linked operation truth: `open` before dispatch; `pending` when work is queued; `submitted` while Stripe reports pending/requires_action; `unknown` while outcome cannot be established; `failed` while the obligation remains due after a definitive failure; `succeeded` only when the full obligation amount is provider-confirmed refunded. If provider returns partial success or multiple linked refund records are observed, do not mark the obligation succeeded until the confirmed total equals its amount; preserve the uncovered remainder as owed and visible.

Durable queue commands are idempotent. Initial dispatch is keyed by the refund `operationId`; retry/reconcile administrative commands use a separate request UUID and bind actor, operation, action, and canonical body. Duplicate command IDs replay the saved response; changed actor/action/body conflicts. Work claims use a lease and `SKIP LOCKED`; a crashed lease is recoverable. Provider create always uses the same persisted refund operation UUID as Stripe idempotency key. Reconcile retrieves the exact stored provider Refund ID and never creates/resends. If there is no authoritative Refund ID after an uncertain create, retry uses the original idempotency key and exact allocation; it never makes a fresh key.

Provider response mapping: `pending|requires_action` → `submitted`; `succeeded` → `succeeded`; `failed|canceled` → `failed` and remains owed. A failed object with a stored provider ID cannot be retried as a new create request in W07.5; it is visible for exact-object reconciliation and manual review pending the human's allocation-transfer decision. Definitive create rejection before a provider Refund ID exists can retry with the same persisted key/body. Timeout, connection reset, and 5xx → `unknown`; do not invent success/failure. Persist only allowlisted safe codes. Do not store or expose Stripe response bodies, secret keys, card data, or raw provider error text.

Stripe create uses the trusted PaymentIntent ID from verified `app_payments`, the persisted operation `amount_cents`, `currency=usd`, and idempotency key equal to the persisted operation UUID. No caller-supplied payment, amount, recipient, mode, account, or provider identifier. MVP uses the configured platform account; provider account is stored as `''` unless Connect is explicitly added. Current Stripe docs support amount in minor currency units and creating by PaymentIntent; refunds can be partial. The provider adapter should map these documented Refund statuses and retrieve a specific refund by ID: [create refund](https://docs.stripe.com/api/refunds/create), [retrieve refund](https://docs.stripe.com/api/refunds/retrieve), [Refund object](https://docs.stripe.com/api/refunds/object).

## Browser contract

All responses use `{ok:true,data,correlationId}` or `{ok:false,error:{code,safeMessage,retryable,correlationId},correlationId}`. Private responses are `no-store`. The shared browser types live in `src/refunds.contract.ts`; provider IDs and raw errors are never returned.

| Operation | Actor/input | Response |
|---|---|---|
| `GET /api/admin/refunds?cursor=&limit=` | Admin; bounded cursor and `limit` 1–50 | `RefundListDTO {items: RefundObligationSummaryDTO[], nextCursor}` |
| `GET /api/admin/refunds/:obligationId` | Admin; UUID | `RefundDetailDTO` including payment balance and operation history |
| `POST /api/admin/refunds/:obligationId/dispatch` | Admin; `{operationId}` UUID; amount/provider config derived server-side | `RefundActionDTO {operation: RefundOperationDTO, obligation: RefundObligationSummaryDTO}` after durable operation and dispatch job commit; does not claim Stripe called or refund settled |
| `POST /api/admin/refund-operations/:operationId/retry` | Admin; `{requestId}` UUID; retry exact operation and allocation | Same `RefundActionDTO`; only a definitive failed/unknown operation with safe retry policy may be queued; unknown always reuses original idempotency key |
| `POST /api/admin/refund-operations/:operationId/reconcile` | Admin; `{requestId}` UUID | Same `RefundActionDTO`; queues a read-only provider reconciliation; no resend |

`RefundObligationSummaryDTO` fields: `obligationId, source, state, amountCents, currency:'USD', createdAt, updatedAt, memberName, tableTitle, reservedCents, availableCents, latestSafeCode, canDispatch, dispatchBlockedReason`. `reservedCents` is payment-wide owed/reserved balance; `availableCents` is capped to the remaining amount owed on this obligation and payment-wide uncommitted balance, so it can never exceed this obligation's amount. `latestSafeCode` is null unless a persisted allowlisted provider code exists; ordinary states like `open` are not error codes. `dispatchBlockedReason` is `null|'balance_reserved'|'operation_in_progress'|'manual_review'|'settled'|'provider_unavailable'`. A terminal failed operation is `manual_review` at the obligation level; the operation detail separately states whether same-key retry is safe. Eligibility is server-derived; the client must not infer it from amounts.

`RefundDetailDTO` adds `paymentAmountCents, refundedCents, operations`. Each `RefundOperationDTO` is `{operationId,amountCents,state,createdAt,updatedAt,safeCode,canRetry,canReconcile}`. Operations are newest first. `canRetry` is false for `safeCode='payment_mismatch'` even though no Refund ID is stored, because the provider may have created an object that could not be safely bound. Both action booleans are false while provider/worker readiness is unavailable; the admin sees service-unavailable state instead of an action that will predictably fail. `RefundActionDTO` returns the updated operation and obligation summary. Member refund remains owner-scoped through existing `GET /api/me/seats` and `GET /api/me/seats/:seatId`; those DTOs contain only the member's obligation state/amount and no operation/provider identifiers.

Safe error codes: `unauthenticated`, `forbidden`, `not_found`, `invalid_input`, `conflict`, `operation_conflict`, `balance_exhausted`, `not_retryable`, `not_reconcilable`, `already_settled`, and `temporarily_unavailable`. Same privacy behavior applies to cross-member/unknown IDs. Infrastructure failures are retryable and never become auth/financial truth.

## Server ownership and verification

Relay owns additive migrations, service-only RPCs, database types, server contracts/repositories/services, provider adapter, worker command, and unit/guarded DB acceptance scripts. Finn owns TanStack route bindings and browser surfaces. Routes must pass cookie-verified actor identity; authorization is repeated inside the service-only RPC. No anon/authenticated role can read or mutate private money tables. Use redacted audit records for admin dispatch, retry, and reconcile. No operation is accepted before migration replay, direct role/ownership DB checks, concurrency/over-refund assertions, provider mocks, and browser evidence are run against the explicitly verified isolated local test target.

The migration is additive, references the draft W07.2 and W07.4 schema, and is not evidence that those drafts have been applied or accepted. This slice must not apply/reset databases or contact Stripe/email. `CHECKOUT_FULFILLMENT_READY` remains false until the checkout webhook and refund worker have been deployed and operationally verified.
