# Quality strategy

## Release decision

This is the W02/W03 test plan and evidence snapshot prepared on 2026-11-12. Later implementation evidence may supersede the row-level status notes below; use the current [acceptance ledger](acceptance-ledger.md) and [task ledger](task-ledger.md) for current acceptance state. This artifact remains useful for its scenarios and coverage strategy, not as the current milestone report.

This strategy covers the W02 foundation and W03 first functional slice: the existing marketing waitlist intake, admin-only app invitation, intercepted email, recipient magic-link activation, member home, sign-out and returning magic link. Its release decision is whether that local journey is safe and coherent enough to become the first working milestone. It is not production-release approval.

Affected actors are visitors/waitlist members, admitted members, admins, and unauthorized anonymous/member/host/restaurant callers. W03 changes admission, identity linkage, email delivery and session authority. It must not create Table offers, profile approval, Seat requests, Seats or charges. The local dev stack is `fifthwheel-rewrite-dev` on API/database ports 56421/56422, with Mailpit intercepting email. Browser acceptance must use the provisioned separate `fifthwheel-rewrite-test` project and 57420–57429 range. Use only synthetic fixtures and reserved `.example` / `.test` addresses. Do not aim the marketing browser form, Supabase CLI or fixtures at a hosted target.

Current evidence includes the guarded W03 Playwright journey and isolated `fifthwheel-rewrite-test` stack with six migrations applied. The baseline local admission/attempt/activation/cooldown harness and DB advisor checks passed. Root independently reran `pnpm test` (123/123), typecheck, build, `git diff --check`, local target self-check and client secret scan. The final `node scripts/run-w03-browser.mjs` journey passed (1/1, 57.3s); its exact synthetic DB fixtures were cleaned, and local Mailpit messages remain intercepted. It compared every marketing row field to a fixture, proved server `received_at` ignored stale client `submitted_at`, checked duplicate row immutability, and queried that honeypot, under-21 and age-121 submissions left no signup/admission/delivery rows. It captured one UI-generated admin operation UUID, made three concurrent protected-route replays, and queried one admission, one delivery and one failed attempt before retry. A seeded deleted admission received the same neutral request-link response as a waiting address with no email; after activation, an immediate returning-link repeat got the same neutral response and only one sign-in link existed. Retry/reconcile retained `failed` then `accepted` attempts, one admission/delivery and one activation audit row; Mailpit stored one invite and reconciliation did not resend. The journey also checked role denials, unknown-address neutrality, invitation replay, tampered verification DTO fields, different-session conflict/sign-out/same-link recovery and safe shared-Table return-path preservation. A separate `node scripts/run-w03-expired-link.mjs` pass requested a real intercepted returning link with local Auth OTP expiry temporarily set to two seconds, followed it after five seconds and confirmed recoverable expiry with no app cookies/session. Its `finally` restored the exact original config bytes (`otp_expiry=3600`), restarted the named local test stack, and removed the exact synthetic fixture; read-only checks confirmed zero matching Auth/signup/admission/cooldown rows. The W03 run captured six synthetic milestone screenshots in `docs/implementation/screenshots/`. After activation/replay the W03 schema has no profile, Table, request, Seat or payment tables; this proves the W03 boundary, not acceptance of later screens. A prior unguarded POST to a hosted waitlist endpoint received no HTTP response; it was not retried. All subsequent runs were local-only. Real email, live providers/data, deployment, charges/refunds and legacy reconciliation remain untested.

## Coverage plan

1. **Fixture and target gate:** provision deterministic role/data fixtures only in `fifthwheel-rewrite-test`; seed by stable IDs and reserved addresses. Before every reset/seed/test, print and assert workdir, project ID and local target. Refuse linked projects, project refs and `--db-url`. Never reset the dev stack or any pre-existing project as part of independent browser tests.
2. **Foundation checks:** on a disposable test DB, apply all migrations from zero; verify RLS/grants for each new table and private function, signup disabled, exact callback allowlist, and that no service-role key occurs in client bundles. A migration unit test alone does not prove server authorization.
3. **Admission integration:** use the current marketing JSON contract against the local app endpoint, with app/email hosts explicitly redirected to the test project and Mailpit. Assert request, stored row, admin list, operation/admission row, intercepted email, actual link redemption, callback, home, sign-out, returning link and refresh in one trace with correlation/operation IDs.
4. **Abuse and boundaries:** drive the same server operations as anon, normal member, uninvited verified identity, admin-only identity, host and restaurant roles. Include caller-supplied user/email/role/admission IDs, cross-user IDs, direct REST, replay/concurrent submits, duplicate normalized email, honeypot, malformed fields and rate-limit bursts. Assert both no unauthorized response and no unauthorized side-effect rows/emails.
5. **Provider uncertainty/recovery:** local fake/intercepted adapter should deterministically support accepted, rejected, timeout-before-send and timeout-after-send. Verify durable attempt state and reconciliation/retry; inspect the actual inbox in Mailpit for duplicate delivery and link contents. No test may claim provider inbox delivery when only acceptance is known.
6. **Browser/manual accessibility:** use real browser contexts and real intercepted links; a test helper may create role fixtures but must not inject the final member session to claim A28/A29. Test fresh context, same-device replay and another-device link. At keyboard-only, phone width and 200% zoom, inspect navigation, focus, form state/errors, recovery and disabled actions. Capture screenshot and environment/fixture references for each gate.
7. **Regression after fixes:** rerun affected API, database and browser paths plus neighboring recovery/authorization paths. Report local test evidence separately from provider/live configuration. Keep all acceptance ledger statuses open until these exact checks run and evidence is attached.

### Reusable W04 test data and execution notes

- Use a unique run prefix and deterministic synthetic identities: `w04-owner-prefs-1` through `w04-owner-prefs-7`, `w04-owner-age-21`, `w04-owner-age-under`, `w04-owner-stale`, `w04-owner-retention`, plus `w04-admin-review`, `w04-host-assigned`, `w04-host-unassigned`, `w04-venue-assigned`, `w04-venue-unassigned`, `w04-other-member`, and an anonymous context. All emails must be reserved `.example`/`.test`; seed/delete only exact run-owned IDs in the test project. Do not use an app-wide reset.
- Keep a fixed server clock/time zone for Atlanta boundary cases; test both immediately before and after Atlanta midnight. Use DOB calendar arithmetic rather than a duration-of-days approximation. Separate age eligibility today from age on a future Table date.
- Profile revisions should capture expected version in every save/submit/review operation. Assert both the returned conflict and unchanged persisted row when an old revision is submitted. A stale form must not lose separately valid fields on conflict recovery.
- For private evidence, inspect signed URL expiry and object ACL/storage policies directly in test, but never log or attach reusable signed URLs to artifacts. Use non-sensitive image fixtures with EXIF metadata to assert the transformed output. Verify audit rows contain actor/action/subject and minimal metadata only.
- The retention policy values are architecture engineering defaults, not final human-approved public policy. Local tests may advance a controllable clock or invoke the bounded cleanup operation; do not alter real records or infer production policy approval from test success.
